7개 세션, 71시간, 1,237번의 도구 호출. Claude Code Opus 4.8로 사주 앱 매각 전략부터 포켓몬 카드 기대값 분석까지 처리했다. 마지막 세션에서는 Claude가 레퍼런스 사이트를 제대로 따라오지 못하는 구조적 원인을 직접 분석했다.

**TL;DR** Dynamic Workflow로 독립 분석을 병렬 처리하면 체감 속도가 크게 달라진다. 단, 브라우저 스크린샷으로 레퍼런스 디자인을 가져오는 건 색감 수준에 그친다. CSS 토큰을 실제로 파싱해야 충실도가 나온다.

## 25시간 세션에서 크레딧 시스템을 프롬프트로 설계했다

이 기간 가장 무거운 세션은 커피챗(AI 면접 SaaS) 세션이었다. 25시간 48분, 365 tool call.

시작 프롬프트: "커피챗 프로젝트 현상황 / 남은 작업 확인해줘 그리고 모바일에서 열었을 때 UI 고려해줘."

전수 감사가 필요한 케이스라 에이전트 8개를 병렬로 돌렸다: 빌드/헬스 점검, 기능 완성도, 모바일 UI 6개 표면(내비·랜딩·이력서·포트폴리오·면접·계정/결제/어드민). 감사 결과가 들어오는 동안 dev 서버를 390px 모바일 폭으로 실제 렌더해서 교차 검증했다.

감사가 끝나자 진짜 무거운 작업이 시작됐다: 크레딧 단가 설계.

```
"이력서 / 포폴 / 면접 20/30턴 각각 sonnet / opus로 했을 때 얼마가 들어?"
→ "30턴에 7000원 정도 나오게 하고 싶어."
→ "보너스 300 정도로 조정해주고, 30턴에 900으로 맞춰줘."
```

API 원가 → 크레딧 환산 → 유저 판매가를 역산하는 과정이었다. 5배 마진을 적용했을 때 30턴이 900크레딧 = 9달러 = 12,000원. 목표 7,000원에 못 미쳤다. 여기서 Claude가 직접 프롬프트 캐싱을 제안했다. 시스템 프롬프트가 고정이라 반복 호출 원가가 최대 90% 줄어든다. `lib/credits.ts`에 캐싱 로직을 구현하고 900크레딧 = 7,000원 목표를 맞췄다.

같은 세션에서 `lib/audit.ts`, `app/api/track/route.ts`, 어드민 페이지, Resend 이메일 인증, PortOne 결제 연동까지 들어갔다. PortOne을 고른 이유는 명확했다: 토스는 해외 결제가 막혀있고, PortOne은 국내 PG와 해외 카드를 한 SDK로 처리한다.

## 5개 에이전트 병렬로 사주 프로젝트 GTM을 분석했다

FortuneLab(사주 앱) 세션: 142 tool call, 14시간 49분.

현황부터 꺼냈다. `STATUS.md`에서 실제 지표를 확인했다:

- 누적 유료 주문 30건 — 전부 KR Toss, 해외 PayPal 0건
- 4월 세션 87회
- 프로덕션이 44일간 배포 끊겨 있었음

"팔아야 돼, 현실적인 수치로 전략 수립해줘"라는 요청에 5개 에이전트를 병렬로 돌렸다: KR 시장 분석, 단위경제(CAC·LTV), 제품 진단, 채널 리서치, 자산 매각 평가. 5개 분석이 같은 결론으로 수렴했다: 트래션이 너무 얇다. 팔기보다 한국에서 피드백을 더 받는 게 맞다.

그래서 X(Twitter) 봇을 만들었다. `lib/xbot/` 디렉토리에 7개 모듈이 생겼다: `cohorts.ts`(타깃 코호트), `formats.ts`, `viral.ts`, `voices.ts`, `rotate.ts`, `xClient.ts`, `generate.ts`. Vercel Cron으로 6시간 주기 발행을 연결했다. 계정 브랜딩 이미지는 `gpt-image-2`로 세 배치에 걸쳐 생성했다.

## 치과 사이트에서 레퍼런스 한계가 처음 나타났다

동백유디치과 리디자인 세션: 274 tool call, 8시간 2분. `mcp__claude-in-chrome__computer`가 64회로 가장 많다. 브라우저 조작과 화면 캡처가 중심이었다는 뜻이다.

"AI 티 없이 상위권 치과 수준으로 예쁘게" — Open Design 루트로 들어갔다. 한국 상위권 치과 사이트를 직접 리서치해서 레퍼런스로 쓰고, 로컬 자산(사진 13장: 외관/대기실/진료실/복도)을 먼저 파악했다.

그런데 반복적인 패턴이 나타났다:

1. 레퍼런스 치과 사이트 스크린샷
2. 결과물 확인 → "AI 티 나", "폰트 통일 안 돼", "배경 너무 정적이야"
3. 다시 레퍼런스 탐색

색감은 비슷한데 구조·폰트·레이아웃이 달라지는 게 반복됐다. 이 문제의 원인은 세션 7에서 직접 분석하게 된다.

## 포켓몬 카드 직구에서 브라우저 자동화가 유용했다

세션 5(104 tool call, 2시간 22분)는 Buyee에서 포켓몬 카드 박스 직구를 탐색하는 세션이었다.

11,803건의 매물을 수동으로 거르는 건 불가능하다. Claude가 한 일:

1. "ポケモンカード BOX" 검색 후 봉인·즉시구매 조건으로 필터
2. 한국 도착가 = 상품값 + 대행수수료(¥800) + 일본 내 배송(¥1,000) + EMS(¥3,500) 계산
3. 박스별 개봉 기대값(EV) 워크플로로 13개 박스 병렬 검증

EV 워크플로가 두 번 연속으로 떴다. 첫 번째는 정가·현재 시세 검증(10개 박스), 두 번째는 개봉 EV vs 봉인 가격 비교(13개 박스). 결과는 HTML 테이블로 정리됐다. 어비스아이가 EV 대비 봉인 가격이 낮아서 가장 효율적이라는 결론이 나왔다.

통관세 관련 질문도 나왔다: "2번 나눠서 주문하면 면세받을 수 있어?" 답은 아니다였다. Buyee에서 나가는 소포는 모두 동일 발송인이라 합산과세에 걸린다. 그리고 의도적 분할은 관세법 위반이다.

## 커피챗 아이콘/파비콘을 세 번 다시 만들었다

세션 6(210 tool call, 3시간 28분)에서는 커피챗 아이콘·파비콘·OG 이미지를 전면 교체했다.

시작은 모의면접 이력서/포폴 입력 칸이 사라진 이유를 추적하는 것이었다. 코드를 보니 사라진 게 아니었다. `InterviewSetupForm.tsx`에서 step3로 옮겨가 있었다. `c6dd46e` 커밋이 step 0(직무)만 개편했고 자료 단계는 건드리지 않았다. 문제가 아니었다.

아이콘 작업이 본 작업이었다. "대기업 교육사이트/강의사이트 참고해서 AI 티 안 나는 걸로 제작해줘"라는 요청에 인프런을 레퍼런스로 삼았다. 그런데 여기서도 같은 문제가 나왔다:

> "지금 모두 다 실제 사이트의 래퍼런스를 가져온 게 아니라 다 똑같이 저품질 AI인데 색만 다른 것 같은데?"

방향을 바꿔 `gpt-image-2`로 직접 생성하는 방식으로 전환했다. `scripts/gen-assets.mjs`로 파비콘·OG·아이콘을 배치 생성하고 `scripts/finalize-assets.mjs`로 후처리했다. 세 배치에 걸쳐 최종안을 확정했다.

이력서와 포폴 필드 구조도 손봤다. 이력서와 동등하게 두고, 없으면 안 넣는 걸로 처리했다. `InterviewInfoModal.tsx`가 이 변경의 핵심 파일이다.

## 래퍼런스 디자인 충실도 문제를 직접 분석했다

세션 7(84 tool call, 4시간 14분)은 치과·커피챗 두 세션에서 반복됐던 문제를 정면으로 다뤘다.

문제 재현: 인프런을 레퍼런스로 지정하면 결과가 어떻게 나오는지 직접 확인했다.

원인은 두 가지였다:

**1. 브라우저 캡처의 해상도 한계**
Claude가 페이지를 스크린샷하면 1280px 전체 이미지가 들어온다. 여기서 시각 패턴을 추출할 때 "민트 계열 + 둥근 버튼" 같은 거친 특징만 읽힌다. 실제 CSS 변수, 폰트 패밀리·웨이트, spacing 값은 이미지에서 읽을 수 없다.

**2. 재현 시 구조 재발명**
레퍼런스의 레이아웃을 "비슷하게" 구현할 때 Claude는 새 구조를 발명한다. 원본의 그리드·컴포넌트 계층을 그대로 이식하지 않는다.

해결책은 `extract-reference.mjs` 방식이다. 대상 사이트의 CSS를 파싱해서 실제 토큰을 `reference-tokens.json`으로 추출하고, 이걸 `:root` CSS 변수에 직접 바인딩한다. `compare-tokens.mjs`로 충실도가 70% 이상인지 검증한다.

이 파이프라인은 이미 `.claude/hooks/design-gate.sh`에 연결돼 있었다. 레퍼런스 URL이 감지되면 `extract-reference.mjs`를 먼저 실행하게 강제하는 구조다. 운영하면서 알고 있었지만, 이 세션에서 왜 필요한지를 직접 확인했다.

## 병렬이 효과 있는 조건과 아닌 조건

이번 7세션에서 패턴이 명확해졌다.

병렬 workflow가 실질적으로 빠른 경우: 분석 단위가 서로 독립적일 때다. 사주 프로젝트 5개 시장 분석, 커피챗 모바일 UI 8개 표면 감사, 포켓몬 카드 EV 13개 박스 검증이 여기에 해당한다. 에이전트 수가 많아도 벽 클락(wall clock)은 가장 느린 단일 에이전트 시간과 같다.

순차가 맞는 경우: 앞 결과가 다음 입력을 결정할 때다. 크레딧 원가 → 마진율 → 크레딧 가격 → 보너스 조정이 그랬다. 여기서 workflow를 돌리면 의미가 없다. 실시간 대화가 빠르다.

래퍼런스 디자인 추출은 두 경우 어디에도 해당하지 않았다. 기술적 한계였다. 스크린샷이 아니라 CSS 파싱이 필요한 작업이었다.
