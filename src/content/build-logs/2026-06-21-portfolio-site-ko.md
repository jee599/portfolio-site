6월 20일 오후, preterview 모바일 화면에서 `window.innerWidth`를 찍어봤더니 **2240px**가 나왔다. 창 크기는 784px인데. 코드를 읽어선 안 잡히는 버그였다 — 실제 런타임에서 측정해야 비로소 보이는 숫자.

**TL;DR** 4세션, 317 tool call. 모바일 UI 24파일 패치, 사업계획서 6편 + 텔레그램 자동 발송, 치과 SERP 6키워드 측정 → 커밋까지 Claude Code 한 사이클로 돌렸다.

## 치과 모니터링, 9분·2 tool call

6월 21일 아침 요청:

```
동백유디치과(dongbaek-uddental) 정기 측정이다. dental-clinic 서브에이전트에 위임해 수행하라.
모니터링 키워드(임플란트 뼈이식·용인 임플란트·동백 임플란트·상악동거상술·동백 치과·용인 소아치과)의
블로그탭/통검 노출순위, inbox 신규 파일 처리, history.json 갱신, sync.sh 실행...
```

직접 처리하지 않고 `dental-clinic` 서브에이전트에 위임했다. **Agent 1번, Bash 1번 — 총 2 tool call, 9분.** 에이전트가 `clinic.json`과 `history.json`·cache를 읽어 컨텍스트를 복원하고, SERP 6키워드를 전부 실측하고, `digests/measure-2026-06-21.md`(10KB)를 생성한 뒤 커밋 `2f49a72`를 푸시·배포까지 마쳤다.

`동백 임플란트` 키워드가 블로그 8→9위로 1칸 내려갔는데, 에이전트 판단은 "로테이션 노이즈"였다. 프롬프트에 "점수 임의 재채점 금지, 측정치만 기록"을 명시해뒀기 때문에 수치를 건드리지 않았다.

단일 치과 전담 에이전트를 쓰는 이유가 이거다. 컨텍스트 복원 → 측정 → 기록 → 동기화 연속 작업을 메인 세션이 떠안지 않는다. 메인 세션은 결과만 받는다.

## 182 tool call, 모바일 UI 전수 수정

가장 부피가 컸던 세션이다. `/effort ultracode`를 켠 상태(xhigh 추론 + 다이나믹 워크플로)에서 시작했다.

```
preterview 사이트 지금 모바일에서 버튼도 깨지고 ui에 영어도 나오고 이상해,
전체적으로 모두 확인해서 이상한게 있는지, 자간이나 엔터를 잘못쳐서 늘어진거 확인해서 모두 고쳐
```

Dev 서버를 백그라운드로 띄우고 `mcp__claude-in-chrome__browser_batch`로 실제 모바일 뷰포트를 확인했다. iPhone 390px로 설정했는데 렌더는 1568px로 나왔다. JS 도구로 `window.innerWidth`를 직접 찍으니 **2240px**. 창 크기는 784px인데 콘텐츠가 2240px로 벗어나고 있었다. 모바일 깨짐의 근본 원인이었다.

정적 코드리뷰로 이걸 잡으려면 오버플로 원인 파일을 일일이 추측해서 좁혀야 한다. 런타임 실측으로 수치를 먼저 확인하고 역추적하는 게 훨씬 빠르다.

한국어 설정인데 영어 버튼이 나오는 문제는 i18n 라우팅 이슈였다. 브라우저 `Accept-Language: en`을 감지하면 `/en`으로 리다이렉트하는 로직이 원인이었다. `i18n/routing.ts`를 수정하고 `messages/ko/` 아래 누락된 번역 키를 채워 넣었다.

수정한 주요 파일:
- `app/globals.css` — 뷰포트 오버플로 루트 원인
- `i18n/routing.ts` — 언어 감지 로직
- `components/interview/InterviewRoom.tsx`, `RadarChart.tsx` — 모바일 레이아웃
- `messages/ko/common.json`, `dashboard.json`, `pricing.json`, `interview.json` 외 — 영어 잔존 번역 키
- admin 페이지 5개 — 모바일 대응 누락

**Bash 46번, Edit 40번, Read 35번, browser_batch 26번 — 총 182 tool call, 4시간.** 수정하고 → 빌드 확인 → 브라우저 리로드 → 화면 캡처 → 다음 이슈로 이어지는 루프였다.

## GTM 분석, 12개 에이전트 병렬

```
preterview 어디에 어떻게 팔아야하는지 분석해줘, product hunt에 올려야돼?
```

기존에 만들어둔 `preterview-global-gtm.html`(25개 리서치 에이전트 결과 + 16개 수치 팩트체크)이 이미 있었다. Product Hunt는 "채널 ④ · SECONDARY · 1일 스파이크"로 이미 다뤄져 있었다.

Workflow로 12개 에이전트를 병렬로 돌려 PH 현황을 검증했다. adversarial verify 패턴 — 헤드라인 수치마다 별도 에이전트가 반박하려는 시도로 검증하는 방식이다. 걸린 게 있었다: "10x/40-50x" 배수는 측정값이 아닌 통설, 8.7%/시간은 2016년 데이터. 이 정정값만 최종 답변에 반영했다.

결론:

> Product Hunt는 "올려야 되냐"가 아니라 "언제 쏘느냐"의 문제다. 지금/첫 채널로는 아니다.

이 세션에서 "GEO / AEO 관련 마케팅 작업이 되어 있어?"라는 물음도 처리했다. Claude가 preterview 코드베이스를 뒤져 구조화 데이터, 메타태그, `sitemap.xml` 상태를 실제로 확인했다. 레퍼런스 URL을 던지면 그 스타일을 분석해 방향을 잡는 것도 이 세션에서 진행했다. **35 tool call, Bash(22) 중심.**

## 사업계획서 6편 + 텔레그램 발송

```
치과광고 프로젝트 / preterview 쓰인 llm 기술적인 부분이나 마케팅적인 부분처럼
기술적으로 / 전문적으로 들어간 부분에 대해서 이해하기 쉽게 디테일하게 분석한
보고서나 사업계획서처럼 문서 2개 만들어주고...결과는 hermes 써서 텔레그램으로 보내줘
```

가장 먼저 한 일은 `~/funding/`을 뒤지는 것이었다. 이틀 전(2026-06-17)에 이미 57개 지원사업을 검증해둔 데이터가 있었다. 바닥에서 다시 리서치하지 않고 그걸 베이스로 핏 분석을 짰다.

생성 파일:
- `01_preterview_기술사업분석.md`
- `02_치과광고자동화_기술사업분석.md`
- `03_지원사업_공모전_투자_핏분석.md`
- `04_사업계획서_preterview.md`
- `05_사업계획서_치과광고자동화.md`
- `06_공고분석_제출서류_체크리스트.md`

마지막으로 `hermes`를 통해 텔레그램 채널에 요약 + 6개 파일 발송까지. **Bash 35번, TaskUpdate 18번, Read 12번, Write 11번 — 총 98 tool call.** 사업계획서 하나에 사람이 최소 이틀은 잡아야 하는 분량을 한 세션에 뽑았다.

세션 중간에 "앞으로 A4 한 장 이상 나오는 답변은 HTML 보고서로 줘"라고 지시를 추가했다. 이후 Claude가 마크다운 대신 HTML 파일을 직접 생성해 브라우저에서 바로 열 수 있게 출력했다. 대화 중간에 출력 포맷을 바꾸는 게 자연스럽게 통한다.

가장 많은 걸 배운 세션은 모바일 디버깅이다. `innerWidth: 2240px`는 코드를 읽어서는 안 나온다. 브라우저 자동화로 런타임에서 실측해야 비로소 잡힌다.
