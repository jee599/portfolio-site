3일 동안 Claude Code를 세 세션 돌렸다. 총 315 tool calls, 수정 파일 29개, 생성 파일 12개. 사업계획서 작성부터 모바일 UI 버그 수정까지 — 작업 성격이 완전히 달랐다.

**TL;DR** 반복적이고 긴 작업일수록 Claude Code가 빛난다. 사람이 쓰면 며칠 걸릴 사업계획서 6개를 한 세션에 뽑았고, 모바일 UI 24개 버그를 브라우저 자동화로 잡았다.

## 사업계획서 6개를 한 세션에: 세션 1

세션 1의 프롬프트는 길었다.

```
치과광고 프로젝트 / preterview 쓰인 llm 기술적인 부분에 대해서
이해하기 쉽게 디테일하게 분석한 보고서나 사업계획서처럼 문서 2개 만들어주고,
지원할 수 있는 현실적인 모든 공모전 / 지원사업 / 투자에 대해서
여러방면으로 검증해서 내 아이템들에 맞는 핏 / 통과확률에 대해서 모두 찾고
이것도 보고서로 줘. 결과는 텔레그램으로 보내줘
```

요구사항을 정리하면 이렇다: 두 프로젝트(preterview, 치과광고 자동화)의 기술·사업 분석 각 1개, 사업계획서 각 1개, 지원사업·공모전·투자 핏 분석 1개, 결과물 텔레그램 전송.

98 tool calls, 27시간 세션이었다. Bash(35), TaskUpdate(18), Read(12), Write(11)가 주력이었다.

Claude가 가장 먼저 한 일은 `~/funding/` 디렉터리를 뒤지는 것이었다. 이틀 전(2026-06-17)에 이미 57개 지원사업을 검증해둔 데이터가 있었다. 그걸 재활용해 핏 분석을 바로 짰다 — 바닥에서 새로 리서치하지 않고 기존 검증 결과를 레버리지한 게 맞는 판단이었다.

결과물:
- `01_preterview_기술사업분석.md`
- `02_치과광고자동화_기술사업분석.md`
- `03_지원사업_공모전_투자_핏분석.md`
- `04_사업계획서_preterview.md`
- `05_사업계획서_치과광고자동화.md`
- `06_공고분석_제출서류_체크리스트.md`

6개 문서를 한 세션에 생성하고 텔레그램 hermes 채널로 전송까지 했다. 사람이 했으면 사업계획서 하나에 최소 이틀은 잡아야 하는 분량이다.

세션 중반에 "앞으로 A4 한 장 이상 나오는 답변은 HTML 보고서로 줘"라는 지시를 추가했다. 이후부터 Claude가 마크다운 대신 HTML 파일을 직접 생성해서 브라우저에서 바로 열 수 있게 출력했다. 이렇게 대화 중간에 출력 포맷을 바꾸는 게 자연스럽게 된다는 게 Claude Code 방식의 장점이다.

## Product Hunt 올려야 돼? — 세션 2

세션 2는 성격이 달랐다. `preterview`를 어디에 팔아야 하는지, Product Hunt에 올려야 하는지 판단해달라는 요청이었다. 35 tool calls, Bash(22) 중심이었다.

Claude가 먼저 한 일은 이전 세션에서 만들어둔 `preterview-global-gtm.html`을 읽는 것이었다. 거기에 이미 25개 리서치 에이전트 결과 + 16개 수치 팩트체크가 담겨 있었다. Product Hunt는 "채널 ④ · SECONDARY · 1일 스파이크"로 이미 다뤄져 있었다.

Workflow 도구로 12개 에이전트를 병렬로 띄워 PH 현황을 검증했다. 여기서 adversarial verify 패턴을 썼다 — 헤드라인 수치마다 별도 에이전트가 "이게 진짜 맞는지" 회의적으로 검증하는 방식이다. 결과로 과장된 수치가 걸렸다: "10x/40-50x" 배수는 측정값이 아닌 통설, 8.7%/시간은 2016년 데이터. 이런 걸 잡아내고 나서야 최종 판단이 나왔다:

> Product Hunt는 "올려야 되냐"가 아니라 "언제 쏘느냐"의 문제다. 지금/첫 채널로는 아니다.

SEO/AEO 현황 확인도 이 세션에서 진행했다. "GEO / AEO 관련 마케팅 작업이 되어 있어?"라는 물음에 Claude가 실제로 `preterview` 코드베이스를 뒤져 구조화 데이터, 메타태그, `sitemap.xml` 상태를 확인했다. 레퍼런스 URL을 던지면 그 스타일을 분석해 방향을 잡는다 — 이것도 Claude Code 방식이 편한 케이스다.

## 모바일 UI 24개 버그: 세션 3

세션 3이 가장 작업량이 많았다. `/effort ultracode`를 켠 상태(xhigh 추론 + 다이나믹 워크플로 모드)에서 시작했다.

```
preterview 사이트 지금 모바일에서 버튼도 깨지고 ui에 영어도 나오고 이상해,
전체적으로 모두 확인해서 이상한게 있는지, 자간이나 엔터를 잘못쳐서
늘어진거 확인해서 모두 고쳐
```

182 tool calls, 4시간. Bash(46), Edit(40), Read(35), `mcp__claude-in-chrome__browser_batch`(26)가 주력이었다.

디버깅 과정에서 흥미로운 장면이 있었다. dev 서버를 띄우고 Chrome 도구로 390px iPhone 뷰포트를 시뮬레이션했더니 렌더는 1568px로 나왔다. JS 도구로 `window.innerWidth`를 직접 찍었더니 **2240px**였다. 창 크기는 784px인데 콘텐츠가 2240px로 벗어나고 있었던 것이다 — 모바일 깨짐의 근본 원인이었다.

정적 코드리뷰로 이걸 잡으려면 오버플로 원인 파일을 일일이 추측해서 찾아야 한다. 실측으로 수치를 먼저 확인하고 거꾸로 원인을 추적하면 훨씬 빠르게 좁혀진다.

한국어로 설정했는데 영어 버튼이 나오는 문제는 i18n 라우팅 이슈였다. 브라우저 `Accept-Language: en`이 감지되면 `/en`으로 리다이렉트되는 로직이 원인이었다. `~/preterview/i18n/routing.ts`를 수정하고 `messages/ko/` 아래 누락된 번역 키를 채워 넣는 방식으로 해결했다.

수정한 주요 파일:
- `app/globals.css` — 오버플로 근본 수정
- `i18n/routing.ts` — 언어 감지 로직 수정
- `components/interview/InterviewRoom.tsx` — 모바일 레이아웃
- `messages/ko/common.json`, `dashboard.json`, `pricing.json` 외 — 영어 잔존 번역 키 제거

총 24개 파일 수정. 수동으로 하면 각 파일을 열고 찾고 고치는 사이클을 24번 돌아야 한다. Claude는 패턴을 파악한 후 Edit 40번으로 처리했다.

## 3세션에서 드러난 패턴

**컨텍스트 재활용이 핵심이다.** 세션 1에서 기존 `~/funding/` 검증 데이터를 재활용했고, 세션 2에서는 이전에 만든 GTM 문서 위에서 시작했다. 매번 바닥에서 시작하지 않고 기존 결과물을 레버리지했다.

**adversarial verify 패턴이 리서치 품질을 올린다.** 단순히 정보를 모으는 게 아니라, 각 주장을 별도 에이전트가 반박하려는 시도로 검증한다. 세션 2에서 PH 관련 수치 오류를 잡아낸 게 이 패턴이었다.

**브라우저 자동화가 UI 디버깅을 바꿨다.** `innerWidth: 2240px`는 코드를 읽어서는 나오지 않는 값이다. 실제 런타임에서 측정해야 한다. `mcp__claude-in-chrome__browser_batch`가 이 측정 단계를 자동화해준다.

3세션 합계: Bash 103회, Edit 48회, Read 47회.
