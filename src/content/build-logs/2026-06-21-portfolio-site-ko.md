9개 세션, 584번의 도구 호출, 수정된 파일 69개. 지난 이틀 동안 preterview와 JDLab 두 프로젝트를 Claude Code로 집중 작업했다.

**TL;DR** 멀티 에이전트 워크플로우로 10개 도메인을 병렬 감사해 버그 77개를 찾았고, 회의적 검증(adversarial verify)으로 46개만 살렸다. 모바일 UI 깨짐은 브라우저 자동화 실측으로 `innerWidth: 2240px` 오버플로를 잡았다.

## 10개 도메인 병렬 감사: 162번의 도구 호출

세션 2는 이번 작업 중 가장 규모가 컸다. 시작 프롬프트는 단순했다:

```
preterview ui/ ux나 기능상에 자잘한 버그들 없나 모두 찾아봐
```

컴포넌트 ~9.4K줄, 페이지 ~5.4K줄, lib ~4K줄, API ~3.2K줄짜리 Next.js 앱을 사람이 직접 읽으면 며칠은 걸린다. 대신 10개 도메인(인터뷰 룸, 이력서 빌더, 포트폴리오, 인증, 결제, 대시보드, 관리자, 랜딩, i18n, 공통 컴포넌트)에 finder 에이전트를 병렬로 띄웠다.

워크플로우 흐름은 세 단계였다:

1. **10개 finder 병렬** → 도메인별로 실제 소스를 읽어 의심 건 수집
2. **회의적 검증** → 각 발견 건마다 별도 에이전트가 실제 코드에 다시 대조, false positive 제거
3. **중복 병합·우선순위** → 겹치는 건 하나로 합쳐 최종 목록 생성

결과: 77건 발견 → 21건 기각 → 56건 확정 → 중복 병합 후 **46건**. severity별로는 high 2, medium 8, low 26, nit 10이었다.

이 과정에서 Claude가 "회의적 검증 에이전트가 실제 소스에 대조해 control flow를 다시 확인했다"고 설명한 대목이 핵심이다. 단순히 "이럴 것 같다"로 버그를 올리는 게 아니라, 실제로 코드를 다시 읽어 확인한 것만 남긴다.

가장 많이 반복된 테마는 **다국어 누락** — 한국어 UI인데 영어 fallback이 그대로 노출되는 케이스가 여러 컴포넌트에 흩어져 있었다.

## "정말 고쳐야 하나" 2차 검증

46건을 바로 고치지 않고 한 번 더 물었다:

```
고쳐야하는 것들 모두 진짜 고쳐야하는지, 고치고 나서 사이드 이슈는 없는지,
중요한 순으로 일단 모두 검증해줘 글로벌 서비스 / 유저사용성 / 보안 / 토큰 낭비는 없는지
```

이 단계에서 각 버그마다 네 가지 렌즈(글로벌 서비스 / 사용성 / 보안 / 토큰 낭비)로 재스코어링했다. 수정 제안에 사이드이펙트가 있으면 걸러냈다. 실제로 이 검증을 거쳐 "불필요한 수정"으로 분류된 건들은 제외하고, 최종적으로 24건의 수정을 `Edit` 57번으로 반영했다.

변경된 파일 목록만 봐도 범위가 드러난다: `auth-context.tsx`, `InterviewRoom.tsx`, `storage.ts`, `lib/format.ts`, `messages/ko/*.json`, `messages/en/*.json` 등 앱 전방위.

## 모바일 UI: 브라우저 자동화로 `innerWidth: 2240px` 잡기

세션 9(182번의 도구 호출, 4시간)는 시작부터 달랐다. 모바일에서 버튼이 깨지고 영어 텍스트가 섞여 나온다는 보고였다.

정적 분석만으로는 한계가 있어서 `mcp__claude-in-chrome__browser_batch`로 실제 브라우저를 띄워 확인했다. 390px iPhone 뷰포트를 설정했는데 렌더는 1568px로 나왔다. JS 도구로 직접 `window.innerWidth`를 찍어보니 **2240px**.

페이지가 가로로 넘쳐서 축소 렌더되고 있었다 — `viewport` 메타 설정 문제였다. 이걸 정적 코드리뷰로 잡으려면 오버플로 원인 파일을 일일이 찾아야 하는데, 실측으로 수치를 먼저 확인하고 거꾸로 원인을 추적하니 훨씬 빠르게 좁혀졌다.

수정 범위: `app/globals.css` 오버플로 처리, `layout.tsx` 뷰포트 설정, `InterviewRoom.tsx` 모바일 레이아웃, `i18n/routing.ts` 언어 감지 로직, 각종 `messages/ko/*.json` 한글 누락 채우기.

## 도메인 교정: 삽질 흔적도 기록

JDLab 작업(세션 1, 3, 4, 6)에서 반복된 삽질이 하나 있었다. `tryjdlab.com`과 `jidonglab.com` 도메인 역할이 여러 파일에 뒤섞여 있었는데, 세션 4에서 공개 사이트는 `jidonglab.com`, 발신자 이메일은 `jd@tryjdlab.com`으로 분리했다. 그런데 세션 6에서 `tryjdlab.com` 자체가 유효하지 않은 플레이스홀더라는 게 밝혀져 다시 정리했다.

이런 연쇄 교정이 필요했던 이유는 처음 설계 당시 도메인 역할이 명확하지 않은 채로 여러 파일에 하드코딩됐기 때문이다. footer 모듈, 프롬프트 빌더, 설정 JSON, 테스트 fixture까지 12개 파일을 한 번에 찾아 고쳐야 했다.

## 멀티 에이전트에서 배운 것

가장 유효했던 패턴은 **발견 → 회의적 검증 → 재검증** 3단계다. 1단계에서 많이 올리고, 2단계에서 false positive를 걸러내고, 3단계에서 수정 사이드이펙트까지 확인하면 실제로 "고칠 필요 없는 것을 고치는" 실수가 크게 줄었다.

브라우저 자동화(`mcp__claude-in-chrome__browser_batch`)는 모바일 깨짐처럼 "실제로 렌더링이 어떻게 되는지"를 봐야 하는 케이스에서 정적 분석보다 훨씬 빠른 진단을 준다. 코드를 읽어서 "아마 이럴 것 같다"는 추론과, 직접 `window.innerWidth`를 찍어서 2240px를 확인하는 건 디버깅 속도가 다르다.
