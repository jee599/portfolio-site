발송 금지된 주소에서 이메일 17개가 실제로 나갔다.

`jd@jidonglab.com`은 preterview의 주 메일박스다. JDLab 로컬커머스 이메일 시스템에서 이 주소를 발신자로 쓰면 안 된다 — `jd@tryjdlab.com` 별칭을 써야 한다. 그런데 `jdlab_tryjdlab_live_send_launch.sh`가 모든 게이트를 열어놓고(`DRY_RUN=0`, `DRAFT_CREATE_OK=approved`, `LIVE_SEND_OK=approved`) 17개를 실발송했다.

이번 주 13개 세션 동안 벌어진 일들을 기록한다.

**TL;DR** JDLab 발송 사고 원인을 찾아 게이트를 다시 닫았고, 치과 소아 블로그는 발행 다음날 '동백 소아치과' 블로그탭 1위를 찍었다. Preterview 이메일에는 영상을 넣을 수 없다.

## 발송 사고 감사 — Bash 21번, Read 22번

세션 4는 JDLab 전체 워크플로 감사 프롬프트로 시작했다. 실제 로그, 상태 파일, 대기열 아티팩트, 발송/반송 조정 결과물을 전부 읽어서 병목·불안전 로직·과도한 반송 원인을 찾아달라는 요청이었다.

첫 진단에서 모순이 바로 보였다. 전략 문서는 "발송 없음/cron 없음"인데, 마지막 실행 로그는 `classification=live_send`, `sent_count=17`이었다. `Bash` 21번, `Read` 22번, `Edit` 14번으로 79 tool calls를 써서 루트 원인 3개를 확정했다.

**RC1** — live-send 런처가 모든 게이트를 하드코딩으로 열어놓았다. `JDLAB_DRY_RUN=0`, `LIVE_SEND_OK=approved`가 스크립트에 박혀 있었다.

**RC2** — 금지 발신자 게이트가 엉뚱한 걸 검사했다. `--expect-profile` 문자열(`jd@tryjdlab.com`)을 보는데, 실제 인증된 Google 프로필은 `jd@jidonglab.com`이었다. 검사 자체가 우회되고 있었다.

**RC3** — `done` 상태가 외부 리포트에서 "처리 완료"로 표시되는데, 실제로는 발송이 아직 안 된 상태일 수 있었다. 오해를 부르는 상태 매핑이었다.

세션 5는 고도화 follow-up이었다. "모든 과정 고도화, 수정 고쳐"라는 한 줄 프롬프트로 4개 독립 감사를 병렬로 돌렸다 — `Bash` 30번, `Edit` 18번, `Read` 16번, 89 tool calls. never-send regex에 구멍(`mailer_daemon` 언더스코어 변형)이 있었고, placeholder/typo 이메일 탐지가 없었고, opt-out 처리가 missing이었다. 전부 닫았다.

## Preterview 이메일에 영상을 넣는 법은 없다

세션 3은 303 tool calls였다. preterview 판매용 콜드메일을 만드는 세션인데, 핵심 삽질이 있었다.

"▶ 30초 데모 — 클릭하면 실제 면접 화면이 재생됩니다"라는 버튼을 넣었는데 재생이 안 됐다. 이메일 클라이언트는 `<video>` 태그를 지원하지 않는다. GIF로 바꿨다. 그것도 제대로 안 왔다. `<img>` 썸네일 + 외부 링크로 바꿨다. 그것도 복잡해졌다. 결국 대화가 이어지면서 "해결 못 할 거면 그냥 빼"라는 결론이 났다.

이메일 HTML은 제약이 많다. `<video>`, `<script>`, 외부 폰트 로딩, 많은 CSS 속성들. 이걸 처음부터 알고 GIF 썸네일 + 링크로 시작했으면 20+ 프롬프트 교환이 필요 없었다. 영상이 이메일에서 재생된다는 전제가 잘못됐고, 그걸 확인하는 데 시간이 걸렸다.

세션 3 산출물: `preterview-email.html`, `preterview-email-univ.html`(대학취업지원센터용), `cold-emails.md`(국내 72개 + 해외 113개 IT 교육기관 타깃 리스트), `send_outreach.py`. `mcp__claude_ai_Gmail__create_draft` 20번으로 Gmail 임시보관함에 초안을 쌓았다.

## 치과 블로그 소아 글, 발행 다음날 1위

동백유디치과 세션이 이번 주에 3개 있었다 (세션 1, 6, 7).

세션 7은 `dental-clinic` 서브에이전트에 위임해서 처리하는 패턴이었다. "유디치과 프로젝트 현황 파악하고 블로그 글 다음꺼 초안 / 플레이스 정보 수정할거 있는지" 한 문장으로 시작했다. `SendMessage` 3번으로 같은 에이전트 인스턴스를 이어 호출하면서 컨텍스트를 유지했다.

6/25 기준 현황: 1편(임플란트)이 6/23~24 경쟁사 도배로 블로그탭 12위 밖으로 밀렸다가 3위로 복귀했다. 2편(소아치과, "용인 소아치과 아이 첫 치과 언제 가나요")을 당일 발행 승인했다.

세션 6(6/26) 측정 결과: 소아 글이 발행 하루 만에 '동백 소아치과' 블로그탭 **1위**, '용인 소아치과' **4위** 첫 진입. `blog_probe.py`로 logNo 224326926066 교차확인 완료.

플레이스 데이터도 나왔다. 유입 -23%인데 예약 전환 +50%, 취소 +125%. 시술 유입키워드 0% — TOP5가 전부 브랜드+지역(유디치과 37.9%, 동백유디치과 20.9%, 치과 15.3%). 신환이 시술 검색으로 안 들어온다는 가설이 데이터로 확정됐다.

## 지원사업 서칭 — 8각도 병렬, 36건 실검증

세션 2와 9는 지원사업 서칭이었다. "치과광고대행 / AI 모의면접에 핏하게 맞는 지원사업을 지금 기준으로 서칭해서 통과확률까지 정리해 달라"는 프롬프트였다.

이미 6/22에 42건 라이브 검증이 끝나 있었다. 이걸 기반으로 "오늘(6/24) 기준 아직 열린 것만" 재검증하는 방향으로 갔다. `Workflow`로 14건 재검증 + 4건 갭 스윕, 18개 에이전트 병렬 실행, 211 tool calls.

세션 9에서는 갭 스윕을 한 번 더 돌렸다. 8각도 병렬 서칭 → 38개 후보 → 중복 제거 36건 → 실검증 36건 → 추천 23건. 결과물은 `~/reports/funding-fit-2026-06-24.html`. 보건업 제외(치과), 서울AI허브 서울사업장 필요, 판교밸류업 dental 부적합 등 실측에서 나온 제약 조건들이 메모리에 반영됐다.

preterview IR도 이번 주에 고도화했다 (세션 8). 기존 IR을 코드베이스로 검증하고, VC·포지셔닝·내러티브·디자인 4개 렌즈로 비평한 뒤 12슬라이드를 재빌드했다. "역량 3축"이 IR에 적혀 있었는데 실제 제품은 역량 5축이었다. 이런 불일치를 검증 에이전트가 잡아냈다.

## 이번 주 수치

13세션, 9개 작업 영역. tool call 총합: `Bash` 250+, `Read` 150+, `Edit` 150+, `Write` 25+. 가장 무거운 세션은 3번(303 tool calls), 5번(89), 8번(92). `ultracode` 모드로 워크플로를 돌린 세션이 3개였다.

단일 세션에서 여러 프로젝트를 섞어 처리하는 패턴이 자주 나온다. 이게 효율적인지는 모르겠다. 컨텍스트가 흩어지는 단점이 있고, 세션 3처럼 하나의 대화가 22시간 넘어가기도 한다. 반면 `dental-clinic` 서브에이전트처럼 전담 에이전트를 쓰면 `SendMessage`로 이어받아서 컨텍스트를 유지하는 게 된다. 어떤 게 낫다고 단정하기보다, 프로젝트 성격에 따라 다르게 라우팅하는 게 지금 방식이다.
