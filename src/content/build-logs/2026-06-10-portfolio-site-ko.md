한 세션에서 917번의 도구를 호출했다. 실행 시간은 70시간 56분. Edit 232번, Bash 412번, Read 163번, Write 50번, 브라우저 자동화 26번이었다.

**TL;DR** 치과 마케팅 자동화 에이전트를 처음부터 설계했다. 가장 큰 교훈은 "단일 세션에 너무 많이 쑤셔 넣지 말 것"이었다.

## 시작: 보고서 하나 띄우려다 시스템 전체를 만들었다

처음 프롬프트는 단순했다.

> "아까 진행하던 치과 보고서 관련해서 보고서 띄우는거야. 직접 클로드 크롬 써서 검증해서"

근데 첫 번째 벽이 바로 왔다. 네이버 스마트플레이스 데이터를 긁으려니 자동화 방지에 막혔다. 우회할 방법을 찾는 데만 꽤 시간을 썼고, 결국 방향을 바꿨다.

네이버 검색광고 API + 원장님이 직접 캡처해서 넘겨준 스마트플레이스 통계 PDF/PNG를 분석하는 방식으로. 자동 수집보다 느리지만, 실제 데이터 소스가 생겼다.

## 보고서 구조가 3번 바뀌었다

처음엔 보고서 하나였다. 대화가 이어지면서 요구사항이 쌓이더니 결국 3개가 됐다.

**원장님용 진단 보고서** — 현재 채널 현황과 개선 방향. 비전문가가 읽어도 이해되게. **내부 작업리포트** — 실행 플레이북. 광고 예산, 키워드, 우선순위 포함. **트래킹 대시보드** — `~/dental-promo/_tracker/index.html`. Vercel에 배포해서 외부에서도 접근 가능하게.

각 보고서마다 수정 요청이 10~15번씩 왔다. "로고 크기 60%로", "가운데 정렬", "여백 더", "폰트 일관화"같은 피드백이 대부분이었다.

open-design 스킬 없이 날 HTML을 손으로 수정하다 보니 일관성이 계속 무너졌다. 이게 세션이 길어진 주요 원인이었다. 처음부터 디자인 시스템을 바인딩하고 시작했으면 수정 라운드가 절반은 줄었을 거다.

## GPT Image-2로 블로그 이미지 파이프라인

치과 블로그에서 이미지는 핵심이다. 상위 블로그들을 분석해보니 공통 패턴이 있었다. 카드뉴스 형태, 정보 전달 목적, 로고 하단 삽입, 폰트·색상 일관성.

처음엔 Gemini 일러스트를 썼다가 GPT Image-2로 바꿨다. 한글 라벨이 가능해지면서 카드뉴스 퀄리티가 확실히 달라졌다. `cardnews.py` 스크립트에서 이미지 생성 → PIL로 로고 합성 → 의료법 위반 문구 자동 필터링 순서로 처리했다.

이 로직을 `dental-blog-image-pipeline` 스킬로 만들어 두었다. 다른 치과를 할 때도 그대로 재사용한다.

## 데이터가 가정을 뒤집었다 — 파워링크 분석

처음 가정은 "네이버 파워링크 광고를 해야 한다"였다. 근데 네이버 키워드도구로 실측해보니 달랐다.

`동백 치과`, `동백 임플란트` 같은 지역 키워드가 월 검색 10회 수준이었다. 파워링크를 집행한 치과도 0개. 반면 월 915회의 플레이스 유입 중 80%가 `유디치과`, `동백유디치과` 같은 브랜드 검색이었다.

결론: 파워링크로 얻을 게 없다. 블로그로 `동백 임플란트` 같은 시술 키워드 상위 노출을 잡는 게 우선이다.

이 분석이 원장님 보고서에서 가장 임팩트 있는 내용이 됐다. "2026-06-05 기준 실측 데이터 기준, 파워링크 집행 비효율"이라는 팩트를 숫자와 함께 넣었다.

## dental-clinic 에이전트 설계

세션이 길어지면서 명확해진 게 있었다. 치과별 컨텍스트를 매번 처음부터 설명하는 건 비효율이다.

`dental-clinic` 에이전트를 만들었다. 세션 시작 시 `~/dental-promo/{slug}/clinic.json`, `history.json`, `~/dental-promo/_kb/LESSONS.md`를 자동으로 로드한다. 이전 작업 이력, 광고 계정 정보, 누적된 교훈이 한번에 복원된다.

이후 "동백유디 블로그 써줘"만 해도 이전 맥락을 다 아는 상태에서 시작한다. 같은 치과를 이어서 할 때는 `SendMessage`로 같은 에이전트 인스턴스를 재사용해서 컨텍스트를 유지한다.

## 병렬 에이전트로 시장 조사 — 22개 동시 실행

사주(FortuneLab) 프로젝트에서는 동적 워크플로우 패턴을 썼다. 수익화 전략 10가지를 리서치할 때, 11개 토픽을 병렬 조사하고 각각 반박 검증했다. 총 22개 에이전트, 약 916k 토큰.

```javascript
const results = await pipeline(
  TOPICS,
  topic => agent(`Research ${topic.name}`, { schema: FINDING_SCHEMA }),
  finding => agent(`Adversarially verify: ${finding.claim}`, { schema: VERDICT_SCHEMA })
)
```

단일 에이전트로 돌리면 컨텍스트가 터지거나 결과가 편향된다. 병렬 조사 + 반박 검증 패턴을 쓰면 숫자 신뢰도가 올라간다. 조사 결과에 "verified / adjusted / unverified" 레이블을 붙여서 어떤 숫자를 믿을 수 있는지 명확히 했다.

## 이번 세션들에서 배운 것

**컨텍스트 두 번 압축된 세션은 절반 효율이다.** 917 tool call 세션은 중간에 컨텍스트가 두 번 압축됐다. 앞 작업 내용이 희미해진 채로 뒷 작업을 이어가다 보니 일관성이 깨졌다. 큰 작업은 처음부터 세션을 쪼개야 한다.

**날 HTML은 디자인 시스템 없이 반복 수정하면 발산한다.** open-design 스킬을 처음부터 쓰거나, 아니면 최소한 CSS 변수로 토큰을 고정해두고 시작해야 한다.

**"해야 한다"는 가정을 데이터로 먼저 검증할 것.** 파워링크 사례처럼, 당연해 보이는 전략도 실측 데이터 앞에서 틀릴 수 있다.
